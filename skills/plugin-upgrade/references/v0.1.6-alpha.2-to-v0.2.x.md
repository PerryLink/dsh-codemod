## 1. 这个跨度里什么会坏

| 类 | 破坏 | 结果 | 扫描 |
|---|---|---|---|
| 安装期拒绝 | peer 区间仍止于 `<0.2.0` | `dsh plugin add` / 重启探针**拒绝安装或启动**（不是静默） | `D1` |
| 服务重写 | `settings.register` / `installSection` / `SettingsScope` 删除 | 设置面编译失败或运行期 TypeError；客户端 `settingsScope` 直接缺失 | `D2` |
| 包/服务删除 | `@deepseek-ai/dsh-invariants`、`ctx.invariants`、`<pkg>/invariant` | import 解析失败；组合行只剩 `patch: entry … not found` 警告 | `D3` |
| 槽删除 | `conversation.session.header.leading` → `conversation.header.leading` | 头部贡献**静默消失**（`ctx.slots.inject()` 无声明就不执行回调） | `D4` |
| Remote API 改名 | `readAll`/`readRelated` → `readBytes`；`changes()` → `changes(path)` | 点击/预览路径 TypeError 或空结果 | `D5` |
| 会话格式 | V3 读方拒绝 V4 日志；`tool-result` 内容块消失；`header.system` 被拒 | 读旧日志失败或新日志无法准入 | 未扫描（见 §8） |
| 消息来源 | `{ kind: 'plugin', plugin: … }` 被 V4 拒绝 | 消息准入抛 `producer-owned source kind` | 未扫描（见 §8） |
| 组合覆盖 | 上游删/改名行后旧 override 打空 | `patch: entry "<id>" not found`、`name mismatch … skipping`，**不报错** | 未扫描（见 §8） |

**为什么本地绿灯不可信**：`D2`–`D5` 的删除都不留别名或 deprecation 说明，本地 tsc 只要还编译旧发布类型线就会全绿；`D4` 是纯静默失效。**本扫描器必要但不充分**：干净扫描只证明「没有命中这五条已知接缝」，不是「已适配」；client 半边需要真浏览器断言，`D1` 需要一次真实安装探针。

## 3. D1 · peer 区间仍止于 `<0.2.0`（error）

- **证据**：`migration-0.2.md:36` 原文「peer 范围会被安装期强制：`dsh plugin add` 会拿运行时的版本去比插件声明的 peer 范围，不匹配就拒绝安装」；`migration-0.2.md:209` 要求每条线一个 clause、禁止 `>=0.1.2-rc.1 <0.3.0` 跨代开区间。宿主实现：`packages/boot/app-boot/src/plugin-compatibility.ts:55-75` 的 `unmetRequirements()`——`engines.dsh` 存在则**独占**（peer 全部忽略），否则逐个检查 `@deepseek-ai/dsh` / `@deepseek-ai/dsh-*` 的 peer；`:103-135` 的 `evaluatePluginCompatibility()` 把不匹配变成安装/启动的前置拒绝；调用点 `packages/boot/plugin-manager/src/operations.ts:356`、`:493`、`:680`。
- **检测**：结构化读取每个 `package.json`。`engines.dsh` 有值时只判它；否则判全部 dsh peer。按 `||` 切 clause：显式上界 `<0.2.*` 且无 0.2 正向下界的 clause 视为排除；**所有 clause 都排除**才报 error（未知/无法解析的 clause 一律当作可通过，避免发明失败）。`workspace:*` / `workspace:^` 不报。
- **改法**：把 0.2 线子句补进区间，最小形如 `>=0.1.6-0 <0.2.0 || >=0.2.1-0 <0.3.0`（每个 prerelease tuple 一个 clause）。跨线支持必须同时列两侧；`engines.dsh` 与 peer 只保留一套口径，别让 `engines.dsh` 独占后又指望 peer 兜底。范围之外仍要配运行时特性探测——范围只能表达「能不能装」。
- **验证**：`dsh plugin --profile <p> add <tarball>` 在 0.2.x 宿主上成功；`dsh --profile <p> --dump-config` 无兼容性拒绝；把运行时降到 0.1.x 时区间仍放行。扫描器侧：bad fixture 命中、good fixture 零命中。

## 4. D2 · settings 重写（error）

- **证据**：`migration-0.2.md:60` `packages/settings/settings-file` 被整体删除；`:62-71` 的旧→新表明确 `register(ns, schema, opts)` / `installSection(...)` / `SettingsScope<T>` / `SettingsRegisterOptions` / `applies` 全部删除，`ctx.settings` = `SettingsForms extends Service`（`static inject = ['configEditor','profileContext']`），客户端 `ctx.settingsScope` 与 `settings.plugin.item` 也删除。宿主：`packages/settings/settings/src/index.ts:223` 导出 `SettingsForms`；`grep -rn "SettingsScope" packages --include=*.ts` 零命中（2026-11-01 复核）。
- **检测**：`settings.register(` / `settings.installSection(` / `installSection(` / `SettingsScope` / `settingsScope` / `SettingsRegisterOptions` 的正则命中（注释行与 `//`、`*` 前缀行跳过）。
- **改法**：表单由 profile 条目的 `Config` schema 自动派生；要暴露的字段标 `Volatile<T>`（`z.<type>().volatile()`），读用 `.get()`，跨字段校验 `.check()`，变更监听 `loader/volatile-update`。旧的 `$DSH_HOME/settings.yaml` 只被一次性导入并改名为 `settings.yaml.imported`；被拒 section 只留在改名文件里。
- **验证**：插件在 0.2.x 宿主上挂载后，设置页出现由 `Config` 派生的表单；`grep -rn "settings.register\|installSection\|SettingsScope"` 零命中；`dsh --profile <p> --dump-config` 能看到该 profile 条目。

## 5. D3 · invariants 全部删除（error）

- **证据**：`migration-0.2.md:80-85`：`@deepseek-ai/dsh-invariants` 包、`ctx.invariants`、`InvariantRegistry` / `InvariantInstaller` / `InvariantFailure` / `InvariantError`、每个 `<package>/invariant` 子路径导出、整棵 `packages/runtime-diagnostics/` 全部删除；`sdk-minimal` 的五个 invariant 行消失，仍指向它们的 patch 只打印 `patch: entry <id> not found`。四个 emitter 从「重抛」改为「记录并继续」。宿主复核：`ls packages/runtime-diagnostics` → No such file；`grep -rn "ctx.invariants\|InvariantRegistry"` 零命中。
- **检测**：`@deepseek-ai/dsh-invariants`、任意 `'<pkg>/invariant'` / `"<pkg>/invariant"` import、`ctx.invariants`、四个 `Invariant*` 符号。
- **改法**：删 import、删组合行、删 `invariant` 包的 dev/peer 依赖；把「靠 `INVARIANT` 异常做失败传播」的路径换成插件自己的错误通道（日志 / 自己的 error event / 明确返回值）。
- **验证**：`grep -rn "dsh-invariants\|/invariant['\"]"` 零命中；`dsh --profile <p> --dump-config` 无 `patch: entry … not found`；失败路径的回归测试仍能让调用方看到失败。

## 6. D4 · 被删槽 `conversation.session.header.leading`（error）

- **证据**：`migration-0.2.md:118` 列出删除项「`conversation.session.header.leading`（位置由 `conversation.header.leading` 接管）」。宿主复核：`packages/client/ui-conversation/src/client/contract/slots.ts:259` 声明 `conversation.header.leading`；`grep -rn "conversation.session.header.leading" packages` 零命中。失效机制与 `legC` 的 E3 同源：`ctx.slots.inject()` 只在声明存在时才执行回调，槽删除没有别名、没有 deprecation。
- **检测**：源码/构建物中的字面量 `conversation.session.header.leading`（含 `lib/` 下已提交构建物）。
- **改法**：改用 `conversation.header.leading`，并按新位置的标准 props 重取会话信息；`settings.plugin.item` 已由 `legC` 的 E3 覆盖，本接缝不重复。
- **验证**：`grep -rn "conversation.session.header.leading"` 零命中 + **真浏览器断言**头部贡献实际出现（干净的扫描与 tsc 都不是证据）。

## 7. D5 · workspace-files Remote 改名（error）

- **证据**：`migration-0.2.md:120-127`：`readAll` / `readRelated`（RPC 回调、返回解码后的字节结果）→ `readBytes(path, { range?, baseFile? })`，经 Connection 二进制 RPC 返回原生 `Uint8Array`；工作区级 `changes()` → `changes(path)`（单目标、目录限制在工作区内）；`read(path, { offset?, limit? })` 与 `list(path)` 未变。宿主：`packages/api/workspace-files/lib/typert.remote-client.d.ts:21-25` 的 Remote 方法签名（`changes` 带 `path`、`readBytes` 带 options）。
- **检测**：`workspaceFiles.readAll` / `workspaceFiles.readRelated`；`workspaceFiles.changes()` 空参调用；`{ readAll | readRelated | changes } = … workspaceFiles` 解构。文件里同时出现 `readBytes` 时降级为 `warn`（迁移中，作为 review lead）。
- **改法**：改用 `readBytes` 并处理 `Uint8Array`（文档预览侧的 `addResource`/`setResources` 依赖回调一并接上）；`changes()` 改成 `changes(path)`；`read()`/`list()` 不动。
- **验证**：tsc 对 0.2.x 类型面绿 + 真浏览器里预览/变更流实际工作（二进制结果不是字符串）。
